# Research and implementation limitations

This is a local demonstration, not a production security boundary or a universal semantic layer. It does not establish semantic equivalence between providers or correctness of results. Provider mappings, trust, schemas, credentials, and classifications are manually configured. Only no-auth local fixtures are supported; real authentication and authorization policy enforcement, secret management, remote endpoint allowlisting, tamper-resistant logs, persistent audit and identity are absent. Approval is in-process, not a signed or durable authorization, and covers capability, provider and argument JSON, not server code or endpoint identity. The mock email service never delivers mail.

Timeout/cancellation use AbortSignal for calls where supported; MCP connection and A2A agent-card discovery are not completely bounded, and remote side effects cannot be reliably undone or proved absent after a timeout. No automatic retries are performed. The fixture returns an A2A message; task polling/failure branches are not yet tested with an independent task-producing agent or an official conformance suite. Static JSON Schema compatibility checking is limited to top-level types; runtime validation checks resolved inputs and outputs. No claims of all-protocol interoperability, benchmark superiority, or reduced developer effort are established.

Established techniques include lexing/parsing, JSON Schema validation, registries, adapter patterns, dependency graphs, human approval and tracing. Potential research contributions require a precise formal semantics for cross-protocol capability composition, measurable provenance/authorization guarantees, and controlled evidence of integration-effort or reliability improvements over carefully selected baselines. None is demonstrated as novel here. Conduct a literature review before making a novelty claim.
